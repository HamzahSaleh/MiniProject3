# Validation reflection

I reviewed Jacob Yuill's ten projects using his saved MiniProject2 commit history, monthly plots and reflections. We matched on 39 of the 50 comparisons before discussion. The activity patterns matched for all ten projects, but the recent themes only matched for three. The biggest problems were using different time windows and deciding what counted as recovery. Jacob accepted all 11 proposed changes by message, so the adjudicated labels use the validator values for those disagreements. Agreement after resolution is 100.0% for all five fields.

The work before a gap did not always show that a project was about to stop. IfcOpenShell had normal parser and geometry work before its pause, while pymbar had bootstrap and cleanup work, including a message about pausing bootstrap work. pyts had release and dependency work before its long gap. These are different situations, so I would not use one type of commit as a reliable warning sign. A maintainer being busy is possible, but a gap by itself does not prove that explanation. The monthly counts show when work became quiet; they do not directly show why.

Several projects resumed through specific tasks. LAStools returned with COPC reader/writer work in July 2023. pymbar returned with README fixes and then PMF routines in early 2019. CoastSat returned with documentation and a GEE authentication fix in October 2025. Its [authentication issue](https://github.com/kvos/CoastSat/issues/596) also has a maintainer response during the quiet period, which shows that a lack of commits did not mean the maintainer had disappeared. These examples support describing the observed restart work while being careful about claims about personal motivation.

Small maintenance changes also mattered. CascadeStudio's recorded gap ended with a README change in October 2024, even though that was not a full feature comeback. TensorFlow.js resumed bot dependency updates after its one empty month. The adjudicated labels count both as resumed activity. That is separate from Currentstatus: CascadeStudio is Inactive at the guide's September 30, 2025 cutoff, even if work returned later. CLUE shows the same distinction in another way: it recovered after an older gap but was Inactive at the status cutoff. An older recovery does not guarantee current activity.

The accepted corrections use the same commit window, count documentation and bot work consistently, and keep the first restart separate from a later revival. WoC also includes contributor branches and PR merge records, so those should not be presented as proof that upstream accepted every change. Some theme choices remain subjective, especially formatting and short messages. Jacob's acceptance resolved the differences in this review, but the final agreement measures consensus rather than a fresh independent review. HasRecovered also shows why percent agreement and kappa are different: final agreement is 100.0%, but post-discussion kappa is undefined because every final label is Yes. I also accepted the ten corrections in his review of my projects, so both validation logs now have final adjudicated values.


Jacob's review of my projects led to five activity-pattern changes, three recent-theme changes and two recovery changes. The pattern changes reminded me to consider the whole timeline instead of a recent rise or an earlier rebound. His theme changes separated behavior fixes from general cleanup. For HapCUT2, I accepted No recovery because he judged the single maintainer commit too isolated to show a sustained return, while other records were unmerged PR work. This is a stricter interpretation than simply counting any resumed commit, which I used in the first review. That remaining definition difference should be made explicit in a revised codebook. We resolved all 21 disagreements across the two reviews, but agreement after acceptance does not remove the need for clearer definitions.
